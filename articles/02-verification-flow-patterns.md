# 验证流程形态学：账号注册的几种"门"

> 防御视角笔记 · 第 2 篇
> 主题：账号注册之后，平台如何通过"验证流程"确认一个人是真实且可追责的

---

## 1. 定位：验证码之后还有"门"

第 1 篇讲的是注册**前**的机器识别（CAPTCHA）。但真正决定"这个账号值不值得信任"的，往往是注册**后**的验证流程——它回答的不是"你是不是机器人"，而是：

> 这个账号能不能联系到真人？密码能不能真正归账号持有者所有？

验证码防的是"批量"，验证流程防的是"虚假与失控"。两者是两套体系。

---

## 2. 常见形态一览

```
  即时建号型        验证码型         链接型(magic-link)    人工审核型
  ─────────────────────────────────────────────────────────────►
  零摩擦             中摩擦             中摩擦               高摩擦
  无验证             邮箱 OTP           邮件点链接           人工审批
  无追溯              短信验证码         一键登录             申请短文
```

### 2.1 即时建号型（no-verification）

填表即建号，无任何验证环节。

**代价/风险**
- 对平台：账号可以无限量、无成本生成 → 垃圾账号、刷量、薅羊毛风险最高
- 对真人：零摩擦，体验最好
- 现状：多见于工具/文档/开发者服务（密码本、代码托管、笔记类），它们往往用**后续行为风控**补位

### 2.2 邮箱 OTP 验证码型（email OTP）

注册后向邮箱发送 4-8 位数字码，用户回填后建号完成。

**关键机制**
- 验证的是"**能读到这封邮件**"，代价是邮箱地址本身——一次性邮箱/域名池会降低门槛
- 站点端常见对抗：**封锁临时邮箱域名**（建号时即校验域名，命中即拒绝）
- 强度上限：取决于"邮箱账号的可获得成本"，而非验证码本身

> 观察点：OTP 验证码的提取是个工程细节——页面上的验证码输入框有时没有任何 name/placeholder/aria 语义，只能靠 `maxlength`（4-8 位）+ 祖先文本（"verification code"）等**组合特征**识别。这从侧面说明：验证码输入框的"可被程序精确找到"程度，本身就是一种隐性对抗维度。

### 2.3 magic-link / 链接型（click-link verification）

邮件里放一个**链接**，点击后浏览器内确认。

**关键机制**
- 它验证的是"**持有该邮箱会话的浏览器**"——比输入数字码更直接
- 链接常是**一次性、短时效**的（几十分钟到 72 小时）
- 常见变体：**设密链接**（"点击完成注册并设置密码"）、**一键登录**（无密码，每次点链接进）

**代价**
- 对平台：无法强制要求"记忆密码"，适合低风险场景
- 对自动化：数字码能被程序读取，链接型需要**真实点击跳转**，门槛略高一档；但仍不防"邮箱账户本身被自动化持有"

### 2.4 短信验证码型（SMS OTP）

手机号接收验证码，是当前**强绑定真实身份**的主流手段之一。

**关键机制**
- 手机号在全球多数地区是**实名/准实名**资源，获取成本远高于邮箱
- 对抗：接码平台、虚拟号段、境外卡池——运营方需持续更新号段黑名单
- 合规：GDPR/CCPA/《个人信息保护法》下，收集手机号意味着更高的数据责任

**代价**
- 对真人：最重（需持有手机 + 等短信 + 可能有资费），国际用户还会遇到国际短信延迟/收不到
- 对平台：短信资费成本高，且短信通道本身是攻击面（API 盗刷/轰炸）

### 2.5 知识问答型（knowledge-based Q&A）

注册时回答一个"只有真人才知道"的问题。常见于传统论坛系统自带的防垃圾机制。

**两种典型**
- **静态知识题**：如"本社区服务收费吗？"——答案固定、公开可得。对程序来说是一道"查资料题"，强度依赖题目是否冷门/动态
- **动态计算题**：如"请计算 xxx 命令的输出"——要求执行一个**外部指令**得到答案。这类题对自动化是硬门槛（需要真实执行外部代码），但对真人也是高负担，且存在明显安全边界问题

**代价**
- 对真人：普遍反感，兼容性差
- 对平台：题目池小则被穷举，题目池大则维护成本高
- 现状：集中在自托管论坛/社区，作为低成本反垃圾手段

### 2.6 人工审批型（manual approval / application review）

提交注册申请后，由管理员/运营**人工审批**，通过后才建号。

**关键机制**
- 申请通常要求**填写申请理由/自我介绍短文**——这是自动化最难伪造的一环（生成"合理的长文本理由"远比填表单难）
- 常见于小社区、邀请制、研究型平台（联邦式实例、封闭社区）

**代价**
- 对真人：高摩擦、等待周期不定
- 对平台：人力成本高，扩展性差；但换来的是**社区质量与账号可信度**，通常配合人工审计使用

## 3. 一个容易被误判的现象：看起来推进了，账号其实没建

研究注册流程时最值得警惕的**伪成功**：流程看似一路走完（填表 → 收码 → 提交），但账号并未真正创建。常见成因：

- **code-login 单点登录**：站点用"邮箱 + 验证码"登录而非注册，填完码后跳回登录/首页，**从头到尾没有建号动作**——页面形态与注册几乎无差别，极难仅凭 UI 判断
- **静默拦截**：服务端悄悄丢弃请求（不报错、不重定向），表单停留原地，邮箱也收不到任何信
- **假成功页**：跳转到一个"欢迎/即将完成"页面，但账号记录里并不存在

> 防御视角的启示：**"流程走通"不等于"账号建成"**。做注册流程测试时，唯一的硬性判定标准是——**用这套凭据能否真正登录**，以及**邮箱里是否出现服务端发出的、含账号归属标识的邮件**。单靠页面文案判成功，是自动化测试里最常见的翻车点。

## 4. 形态对比总表

| 形态 | 真人负担 | 平台成本 | 抗批量能力 | 可追溯性 | 典型场景 |
|---|---|---|---|---|---|
| 即时建号 | 极低 | 低 | 极低 | 无 | 工具/文档服务 |
| 邮箱 OTP | 低 | 低 | 中（靠域名封锁） | 邮箱 | 主流注册 |
| magic-link | 低-中 | 低 | 中 | 邮箱 | 无密码登录/低风险 |
| 短信验证码 | 高 | 中-高 | 高 | 手机号 | 金融/实名类 |
| 知识问答 | 中 | 低-中 | 中-高 | 无 | 社区/论坛 |
| 人工审批 | 高 | 高 | 极高 | 强 | 封闭社区/研究平台 |

---

## 5. 结论

- **验证流程的强度，本质上是"验证对象（邮箱/手机号/人工）的可获得成本"**——不是验证码本身
- 现代强平台普遍**组合**：无感 CAPTCHA（防机器）+ 邮箱/短信验证（防虚假）+ 后续风控（防滥用），层层递进
- 对测试与研究者：判断注册流程是否"真正完成"，永远以"凭据可登录"为唯一标准
