# 注册滥用防御矩阵：服务端能做些什么

> 防御视角笔记 · 第 3 篇 · **作者：[DF-Guan](https://github.com/DF-Guan)**
> 主题：抛开"验证码本身"，服务端还有哪些抗滥用手段，以及各自代价

---

## 1. 一个总览：防御是分层的

前两篇讲的是"注册入口"的识别（CAPTCHA）与"注册之后"的验证（流程）。这一篇把视角放大：**服务端在请求落地前后的完整防御层**。

```
  入口层   表单/路由层   身份层      策略层        数据层
  ────────────────────────────────────────────────────────►
  无感挑战   参数校验    邮箱/短信     域名封锁      人工审计
  指纹      CSRF       知识问答     速率限制      行为风控
  WAF       埋点        人工审批     IP 信誉      封号/降权
```

任何单一手段都有短板，**强度来自组合与纵深**。

---

## 2. 逐层盘点

### 2.1 入口层：拦截在到达表单之前

- **WAF / 反爬中间件**：对可疑 UA、无 Cookie、异常请求头直接阻断；部分实现会在连接层就重置（表现为请求失败/空响应）
- **JS 挑战**：先执行一段脚本做"人机握手"，失败则看不到任何表单
- **指纹采集**：把浏览器环境 hash 进会话，异常环境在后续任何一步都能被回溯

**典型代价**
- 误伤正常用户（尤其是隐私保护浏览器、企业网络、公共 IP）
- 强 WAF 对性能与运维复杂度有持续成本

### 2.2 表单/路由层：拒绝不合理的请求

- **CSRF token + 会话绑定**：确保请求来自同一个会话，拒绝"无状态直发"
- **字段埋点 / 时间校验**：记录表单填写耗时、输入顺序、焦点轨迹，低于人类速度的下限即判可疑
- **提交频率**：同会话/同 IP 短时间多次提交直接限流

**典型代价**
- 增加表单逻辑复杂度；埋点数据是隐私敏感数据，需谨慎设计

### 2.3 身份层：让"建号"变贵

这就是第 2 篇的验证流程——邮箱 OTP、短信、知识问答、人工审批。核心思想一句话：**让每个账号都付出一定成本，批量制造就变得不划算**。

**典型代价**
- 体验与转化率下降；短信等有直接资费成本

### 2.4 策略层：按信誉与上下文动态决策

- **临时邮箱域名封锁**：维护"一次性邮箱域名"黑名单，命中即在建号时拒绝。这是性价比极高的手段——一次性邮箱服务的域名可批量注册，但域名池是有限的
- **速率限制 / 滑动窗口**：按 IP、设备、指纹维度限制注册与登录频率
- **IP 信誉**：数据中心的出口 IP、代理/共享 IP 段直接降权；无感挑战（如 Turnstile）的实现就依赖这一层
- **网络策略**：对某些国家/地区的流量直接按政策拒绝

**典型代价**
- 域名封锁有**误杀**风险（被临时邮箱服务商同域的正常用户连带遭殃）
- IP 信誉对"移动网络 / 家庭宽带共享出口"的用户不友好
- 需要在"拦截滥用"与"接纳真实用户"之间持续调参

### 2.5 数据层：事后补救与持续审计

- **行为风控**：注册后的使用行为（留存、内容质量、登录地点漂移）持续打分，异常账号降权/冻结
- **人工审计**：高风险申请人工复核（与审批制配合）
- **关联分析**：多账号间共享设备指纹/IP 的团伙检测

**典型代价**
- 需要数据分析基础设施；人工审计成本高、不可扩展

## 3. 一个关键观察：手段之间的"替代关系"

防御矩阵里最容易犯的错，是把手段当"补丁"堆叠，而没有理解它们的**替代性**：

| 你缺的是 | 可以用什么补 | 代价 |
|---|---|---|
| 实时人工识别 | 无感挑战（指纹/信誉） | 依赖出口信誉，误伤共享 IP |
| 强大的指纹模型 | 短信验证码（强制实名资源） | 高成本、高摩擦 |
| 短信通道成本 | 邮箱 + 域名封锁 | 域名池有限，会被轮换绕过 |
| 成熟的验证码厂商 | 知识问答 + 人工审批 | 体验差、人力高 |

**没有哪一层是免费的**：要么贵在成本，要么贵在误伤，要么贵在人力。防御方只能选择"自己最付得起的代价"。

---

## 4. 测试视角：如何评估一个注册流程的强度

对研究/评估场景，可以按下面这个"压力递增"的清单，观察流程在每一层的行为（**只做合法评估，不做绕过**）：

1. **入口层**：无头环境直接访问，观察是否被 WAF/JS 挑战/空页拦截
2. **表单层**：观察是否存在会话/CSRF 绑定、提交频率限制
3. **身份层**：尝试用公开的一次性邮箱域名，观察是否被拒
4. **策略层**：换不同信誉的出口，观察验证难度是否变化
5. **数据层**：建号后制造异常行为，观察是否被降权/冻结

**诚实评估原则**：一个"看起来很严格"的流程，可能在某层有巨大空档；一个"看起来宽松"的流程，可能靠后续风控兜底。**强度判断必须基于行为结果，而非 UI 观感。**

---

## 5. 结论

- 注册滥用防御是**分层纵深**，不是单一银弹
- 每个手段都有**明确的代价与误伤面**，选择取决于业务形态与成本承受力
- 对研究者而言，理解"哪一层在起作用、哪一层是空档"，比记忆某个具体手段更有价值
